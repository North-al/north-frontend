# Engineering Practices

TypeScript、代码质量、异常处理、性能优化、技术文档、调试和任务交付规范。

## 1. TypeScript

TypeScript 适度严格。

遵循：

- 公共接口明确声明类型。
- 组件 Props 和 Emits 明确声明类型。
- API 参数和返回值具有明确类型。
- 局部类型能够推导时，不重复声明。
- 避免滥用 `any`。
- 不为了消除类型提示制造复杂泛型。
- 不追求没有实际价值的类型体操。

类型服务于代码可读性和正确性，而不是为了展示类型技巧。

## 2. Code Style

函数优先使用箭头函数。

根据对象方法、类方法等语义选择合适的写法，不机械替换。

代码应当：

- 命名清晰。
- 职责明确。
- 保持上下文容易理解。
- 避免过度抽象。
- 避免无意义的文件拆分。
- 避免简单逻辑被包装成复杂工具函数。

不要为简单字段映射创建额外的格式化、转换、处理函数。

不要为了追求极致复用牺牲代码直观性。

## 3. Comments

必要的代码注释应当保留。

尤其是：

- 复杂业务规则。
- 非直观实现。
- 设计意图。
- 特殊边界条件。
- 容易被误修改的逻辑。

不要用注释简单重复代码本身已经表达的内容。

不要为了减少注释而删除有价值的解释。

## 4. Error Handling

根据异常类型和业务场景决定处理位置。

请求层统一处理公共错误，业务层处理特殊业务异常。

不要重复处理同一个错误。

优先使用项目现有异常处理体系。

异步状态中的 `loading`、`error`、`data` 根据项目现有请求封装决定，不额外建立没有必要的状态管理体系。

## 5. Defensive Programming

主动考虑真实存在的边界情况：

- 空值。
- 空数组。
- 接口字段缺失。
- 业务状态异常。
- 异步请求失败。

但不要为了防御极端情况堆积大量 `?.`、`??` 和无意义兜底。

根据接口契约和业务约束决定哪些情况需要处理。

不要在没有业务依据时随意填充默认值。

## 6. Performance

先识别真实问题，再决定是否优化。

不要默认添加：

- KeepAlive。
- 虚拟列表。
- 复杂缓存。
- 额外的懒加载机制。
- 不必要的计算缓存。
- 复杂的响应式优化。

只有当数据规模、渲染行为或实际性能问题确实需要时，才考虑相应方案。

不要为了性能优化而牺牲代码可读性和维护性。

## 7. Documentation

遇到不确定的 API、复杂用法、版本差异或第三方库行为时，优先查阅对应版本的官方文档。

特别关注：

- Vue 3 官方文档。
- Vue Router。
- Pinia。
- 项目使用的组件库。
- 项目使用的构建工具。
- 项目使用的第三方库。

不要根据其他版本的 API 猜测当前项目的实现方式。

编写复杂 Hook 时，可以参考 VueUse 的源码和设计经验。

文档查阅应当服务于实际任务，不需要为了简单修改机械地浏览所有官方文档。

## 8. Debugging

优先通过以下信息定位问题：

- 错误日志。
- 浏览器控制台。
- 实际调用链。
- 相关源代码。
- 接口请求和响应。
- 问题复现过程。

先分析问题原因，再修改代码。

不要在没有分析原因的情况下反复修改代码碰运气。

如果问题来自项目原有实现，应当区分原有问题与本次修改引入的问题。

## 9. Validation

根据本次修改涉及的内容选择验证方式。

| 修改内容 | 可选验证 |
|---|---|
| 类型相关修改 | TypeScript 类型检查 |
| 代码规范相关修改 | ESLint |
| 构建配置或依赖修改 | 项目构建 |
| 普通 UI 或业务修改 | 根据实际影响选择 |

不要求每次修改都执行全部检查。

优先使用项目已有脚本，不擅自引入新的验证工具。

如果检查失败，应区分：

- 本次修改引入的问题。
- 项目原有问题。
- 环境或依赖问题。

当前不要求主动为普通功能编写单元测试，也不主动引入测试框架。

## 10. Delivery

完成任务后简洁反馈：

- 修改了什么。
- 涉及哪些文件，使用相对路径。
- 执行了哪些验证及结果。
- 尚未解决的问题或潜在风险。

不需要输出大段开发总结。

不重复复述整个开发过程。

不要声称执行了实际上没有执行的检查。

## 11. Scope Control

开发任务应当围绕用户提出的目标展开。

不要：

- 顺手重构无关代码。
- 擅自调整项目架构。
- 引入用户没有要求的功能。
- 为未来可能出现的需求提前搭建复杂体系。
- 将简单需求扩展成大型工程改造。

如果发现与当前任务无关但值得处理的问题，可以简要指出，不要擅自扩大修改范围。
