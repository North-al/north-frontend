# API and State

API 请求、数据处理、错误处理和 Pinia 状态管理规范。

所有实现优先遵循项目现有请求体系和状态管理方式。

## 1. API Organization

优先复用项目已有 API 请求封装。

如果项目没有既定结构，可以参考：

```text
src/api/
├── request/
│   └── index.ts
└── modules/
    └── user/
        ├── index.ts
        └── type.ts
```

基础请求层负责提供统一的请求能力。

业务 API 按业务模块组织。

## 2. Axios Request Layer

项目使用 Axios 时，基础请求层应考虑：

- 请求拦截器。
- 响应拦截器。
- 重复请求处理。
- Loading 管理。
- 公共错误处理。

重复请求和 Loading 策略根据请求类型和业务场景决定，不做全局一刀切。

不要为了实现统一请求封装而增加过多抽象层。

## 3. Business API

业务请求统一使用 `fetch` 前缀。

例如：

```ts
export const fetchUserInfo = (params: UserQuery) => get('/user/info', params)
```

业务 API 只关注接口本身。

遵循：

- 按业务模块组织接口。
- 明确 API 参数类型。
- 控制好返回值类型。
- 复用基础请求层的统一能力。
- 不在每个接口重复处理统一响应结构。
- 不无故增加 DTO 转换层。
- 不无故增加响应包装层。
- 不为简单字段映射创建额外格式化和转换函数。

## 4. Response Handling

统一响应结构应由基础请求层处理。

业务模块不应重复编写相同的响应解包、状态判断和数据转换逻辑。

如果项目已有统一响应格式，直接遵循现有设计。

只有业务确实存在特殊数据结构或转换需求时，才增加对应处理。

不要为了追求所谓的分层完整性，引入没有实际价值的数据媒介。

## 5. Error Handling

根据异常类型和业务场景决定处理位置。

**请求层负责公共错误，业务层负责特殊错误。**

请求层适合处理：

- 网络连接异常。
- 请求超时。
- 通用 HTTP 错误。
- 统一响应错误。
- 项目约定的公共错误提示。

业务层适合处理：

- 特定业务状态。
- 业务流程失败。
- 特殊权限或状态限制。
- 需要业务上下文才能处理的异常。

避免同一个错误在请求层和业务层重复处理。

不要为了统一而强制所有异常都在同一层处理。

## 6. Async State

`loading`、`error`、`data` 等异步状态根据项目现有请求封装决定。

不要为了统一管理异步状态而额外建立一套没有必要的状态体系。

请求状态应具有明确的归属：

- 页面私有状态放在页面或页面 Hook。
- 多处共享状态根据实际需求考虑 Store。
- 请求封装已经提供的状态能力优先复用。

## 7. Pinia

优先使用 Pinia Setup Store。

参考目录：

```text
src/stores/
├── modules/
│   └── user.ts
└── index.ts
```

根据项目现有 Store 组织方式决定具体目录，不强制改造已有结构。

Store 只管理真正需要共享的状态。

不要将所有页面状态都塞进 Store。

## 8. Persistence

大部分需要长期使用的项目可以考虑 Pinia 持久化插件。

持久化采用按 Store、按数据范围配置的方式。

适合考虑持久化的数据：

- 用户信息。
- 权限信息。
- 系统配置。
- 明确需要跨刷新保留的业务状态。

不需要持久化的数据：

- 临时 UI 状态。
- 短期交互状态。
- 可以重新获取的临时数据，除非业务明确需要缓存。

不对所有 Store 进行无差别持久化。

每个 Store 应明确自己的持久化范围。

## 9. Data Transformation

优先使用接口已有数据结构和项目现有工具。

对于日期处理、数据格式化、树形结构等常见需求：

1. 检查项目已有工具函数。
2. 检查项目已有依赖。
3. 使用合适的现有能力。
4. 确实没有合适实现时，再考虑自行编写。

工具函数优先保持纯函数和单一职责。

不要为了简单字段映射创建额外转换层。

## 10. Request Lifecycle

不要默认在页面卸载时取消所有请求。

请求是否取消，需要结合任务归属和业务需求决定。

如果请求结果可能被 Store 或其他页面继续使用，不应因为当前页面离开就无条件取消。

共享请求和页面私有请求应区分管理。
